# Performance & Memory Report — v0.2.7+ (post-remediation)

Measured 2026-09-11 on the dev workstation (Windows 11 build 26200, win32 x64, Node 24.19.0,
Electron 43). Supersedes the v0.1.0 report, whose memory section was
**DEVIATION-PENDING** against AM-10's withdrawn 120 MB ceiling.

Generated by `npm run perf` (`scripts/perf-bench.mjs`). Raw JSONL under `perf-out/`.

## Method

Both figures in every row come from the **same run**, because AM-16 budgets a *marginal*
cost and a marginal figure computed against a remembered baseline is worthless:

1. **Bare window** — a minimal Electron app: one `BrowserWindow` showing a blank document.
   The floor Chromium costs before any application code loads.
2. **MediaForge** — the packaged main entry (`out/main/index.js`) idling on the Downloader
   view, no analysis, no download.

Each launch gets its own `--user-data-dir` (Chromium holds a singleton lock on userData, so
overlapping launches otherwise exit immediately and silently contribute one-sample runs),
quits itself after the window so the probe flushes its buffer tail, and is discarded if it
yields fewer than 5 samples.

Sampling: every 2 s via `app.getAppMetrics()`, per PID — `privateBytes`, `workingSetSize`,
`peakWorkingSetSize`, CPU percentage, idle wakeups — plus the main process's
`memoryUsage()` and `monitorEventLoopDelay()` percentiles. "Idle" is the median of each
run's settled tail (last 60% of samples), then the median across launches.

**`privateBytes` is the primary figure** (AM-16): summed working sets double-count pages
shared between the GPU and renderer processes.

### Where the marginal cost sits

Median private / working set per process type, idle:

| Process | Bare window | MediaForge | Marginal (private) |
|---|---|---|---|
| GPU | 68.3 / 112.4 MB | 103.7 / 140.1 MB | **+35.4 MB** |
| Browser (main) | 37.3 / 94.3 MB | 67.3 / 95.0 MB | +30.0 MB |
| Tab (renderer) | 22.8 / 63.5 MB | 31.3 / 79.0 MB | +8.5 MB |
| Utility | 12.0 / 44.0 MB | 11.9 / 44.2 MB | −0.1 MB |

The single largest contributor is the **GPU process**, not JavaScript: the main heap is
4.9 MB and `arrayBuffers` is zero at idle. That is compositor/texture memory, which points
directly at the `backdrop-blur` audit deferred as out-of-scope in the remediation plan
(30 usages in `SearchResultCard.tsx` alone). The renderer's own 8.5 MB is small.

## Status against AM-16 — two targets missed

Recorded as measured, not adjusted, per the remediation plan's instruction: *"If a target is
missed, record the measured value rather than adjusting the target — AM-16 was set from
evidence and should be amended the same way if it turns out to be wrong."*

- **Idle summed private 215.2 MB vs ≤200 MB.** Over by 15.2 MB (7.6%).
- **Marginal 74.8 MB vs ≤60 MB.** Over by 14.8 MB (25%).

AM-16 cites MediaForge's marginal cost as "~47 MB working set / ~46 MB private", derived in
`specs/performance-memory-deep-research.md` §R-01. This run reproduces the **bare-window**
half of that amendment almost exactly (140.4 / 314.0 MB measured against the 142 / 310 MB
AM-16 was written from) but **does not reproduce the ~46 MB private marginal** — it measures
74.8 MB. The working-set marginal (44.3 MB) is close to the cited ~47 MB.

The likely cause is that the original figure was taken on a warm profile, a different window
size, or with the probe off; this harness uses a fresh profile per launch. The honest
conclusion is that AM-16's marginal ceiling was set from a measurement that predates a
reproducible harness, and **should now be re-derived from this one** — either by re-measuring
deliberately and amending AM-16, or by taking the GPU finding above as the work item that
closes the gap.

Neither failing figure is a regression introduced by the remediation pass: the pass targeted
main-process retention and event-loop stalls, and the residual is GPU/compositor memory,
which none of T0–T14 touched.

## What the remediation pass did move

Verified by automated test rather than by this idle measurement, because each is about
behavior under load that a 5-minute idle run cannot show:

| Target | Source | Result |
|---|---|---|
| 1M-line child, main heap flat | T1 soak, `tests/unit/runner.test.ts` | ✅ < 32 MB growth |
| 250 MB update, `arrayBuffers` bounded | T6, `ffmpegUpdater`/`appUpdater` tests | ✅ < 64 MB (was ≥ 250 MB) |
| 1,000-entry playlist, processes spawned | T7, `tests/unit/playlistHydration.test.ts` | ✅ ≤ 40 (was up to 1,000) |
| Routine progress events | T2, `--progress-delta 0.25` + 150 ms coalescer | ✅ ≤ 5/sec/job |
| Cross-volume download | T3/T4 | ✅ rename path, no main-thread stall |
| Locked temp dir aborting the sweep | T5, `tests/unit/robustness.test.ts` | ✅ fixed (was a permanent leak) |
| 5,000-cue transcript | T13 | ✅ bounded DOM (windowed) |

**Not run** (needs a clean VM or live network, neither available in this pass): cold vs warm
launch comparison, idle on Search/Settings views specifically, analyze of a real
1,000-entry playlist end to end, 50-result search ×20, preview/transcript churn ×50, a real
download with cross-volume finalization, and 100 cancel/restart cycles against live
extractors. The unit-level equivalents above cover the mechanisms; the scenarios would cover
the integration.

## Harness usage

```bash
npm run perf                              # build + baseline + 3×60s launches
npm run perf -- --seconds 300 --launches 3   # the run in this report
MF_MEMORY_PROBE=1 npm run dev             # probe only, into <userData>/logs/mem.jsonl
```

The probe is opt-in and off by default. Nothing leaves the machine.
